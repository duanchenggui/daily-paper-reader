Abstract —Jupyter notebooks support open-ended, multi-step assessments in which students build one logical flow across interdependent steps, combining code, written analysis, and generated outputs such as plots. These reflect authentic scientific practice but are hard to grade consistently, since students may make different yet equally valid choices at each step, so a later answer can only be judged in light of the choices a student made earlier. We present an LLM-based autograder for such flow-structured notebook questions. It generates a rubric from a reference solution, then applies a softening pass that relaxes criteria tied to the reference so legitimate alternative paths are not penalized. Each question group is graded in a single model call, so later answers are judged against the student’s own earlier choices, using question-type tags and schema-constrained, low-temperature outputs. Evidence is scored multimodally: code, text, numerical outputs, and figures from code cells. We deployed the tool in a machine-learning course, integrated with Grade-scope, with a pre-submission format check and prompt-injection defenses, and evaluate it both in that live course and against archived submissions graded by staff in earlier terms. We report agreement, cross-model variance, cost, student perceptions, and injection resilience. With low-temperature models, agreement with human scores is often strong, including on the open-ended items the design specifically targets, while run-to-run stability depends sharply on the model’s temperature support. 

Index Terms —Automated grading, large language models, Jupyter notebooks, multimodal assessment, prompt injection. 

I. I NTRODUCTION 

Automated grading has long been standard in large program-ming courses. Enrollments grew, hand-checking code became expensive [1], and code suits machine checking well: run the submission, compare what it produces against what it should, assign points. Computational coursework has since spread well past programming courses. Students in machine learning, data science, statistics, and engineering now work mostly in Jupyter notebooks , where prose, equations, code, printed output, and figures sit in one document and are produced together. A notebook records not only what a student computed, but how they got there and what they made of it. That opens up a different kind of assignment . Rather than asking for a function that passes tests, an instructor can ask a student to take a problem from raw data to a defended conclusion: inspect the data, choose a model, fit it, plot what happened, and argue whether the result is any good. Most notebook assignments stop well short of this: sequences of independent cells with deterministic outputs, which is the part conventional autograders handle. The ones that use the whole

We call these assignments flow-structured . Three things set them apart from single-answer items. The evidence is mixed and interleaved: prose, derivations, code, and figures appear in the combination the task calls for. Dependencies are irregular, since a question may rest on any subset of the cells above it rather than the preceding one, so a cell cannot be judged out of context. And there is no single right answer: students take different routes in solving the notebook questions. Figure 1 shows an example we return to throughout. Q1 asks a student to remove an input feature of their choosing, Q2 to retrain and report how the error moved, and Q3 to interpret the difference. Several features are defensible in Q1, and once one is chosen the right answer to Q3 follows from it. Correctness depends on the student’s own run, so the same analysis can be right in one notebook and wrong in another. The tools built for notebook courses do not cover this. nbgrader combines automatic checks on code with manual grading of everything else [2], leaving the figures, written analysis, and reasoning that runs across cells to the instructor. Automating it raises three problems existing tools leave open. An instructor’s intent has to become a rubric that rewards a good answer even when it arrives by an unexpected route. Each question has to be assembled with the earlier cells it depends on, and its mixed evidence judged against the student’s own numbers rather than a fixed key. And the result has to run on a live class, which means treating submissions as untrusted input, keeping a person in the loop before grades go out, and delivering scores through the platform the course already uses. We describe a workflow built for flow-structured notebooks and report what happened when we ran it in a course. Our

Autograding for notebooks. Conventional notebook tooling automates what unit tests can reach. nbgrader runs instructor-written checks against code cells and leaves free-response work to manual grading [2], a sensible division of labor as long as the free-response part stays small. In flow-structured assignments it does not. LLM-based systems have begun to push past that line, and two are close to our setting. PyEvalAI grades Jupyter notebooks with a local model and a tutor in the loop [5]; Saez et al. benchmark several LLMs on student notebooks and find that even strong models overlook details that change a grade [6]. Both score a notebook question by question, leaving open the case where one answer can only be judged in light of another the same student gave earlier. 

LLM grading of code assignments. Work on programming submissions is further along. JorGPT compares model families and calibration strategies [7], BeGrading fine-tunes smaller models for code feedback [8], and Lewis and Chen summarize code before mapping it onto a rubric [9]. Nagakalyani et al. propose a fine-tuned Code Llama assistant whose rubric rat-ings TAs accept or override, cutting grading time by 24% [10]. Chiang et al. show related risks at course scale (format failures, prompt hacking) in a 1,000+ student NLP class [11]. Those settings still grade text or source as text; a notebook also has student-generated figures, outputs that depend on earlier cells, and prose about both. 

Rubrics, open-ended answers, and reliability. Open-ended grading is hard because no single output defines correct-ness. Pecuchova et al. evaluate LLMs on open-ended higher-education responses and find that model choice largely de-termines whether the result is deployable [12]. A rubric makes such grading auditable without making it easy: Yang and Gulbahar use synthetic rubric-based data to show that even detailed rubrics leave AI and human scores apart [13]. Reliability work adds that raw scores cannot be taken at face value; Korthals et al.’s SURE framework combines self-consistency with selective human review, cutting workload while keeping uncertain cases in front of a grader [14]. We read rubric design, score stability, and selective review as three views of one problem, and evaluate all three for the pipeline we deployed rather than treating reliability as a separate claim. 

Prompt injection. Student text is untrusted input, and the attack surface is by now well documented. Liu et al. for-malize prompt-injection attacks and defenses [3]; Cai exam-ines education-specific attacks, among them rubric mirroring, where a submission recites the grading criteria back at the model [4]; Milani et al. show that hidden text in a submission can move an LLM-assisted grade [15]; and EvalHack pushes answer-side attacks further with stealth Unicode payloads [16]. This work reports what defeats a grader in isolation, and says less about how the same defenses hold up inside a pipeline that must also parse, score, review, and export. 

Where this work sits. No prior system combines all of these: grading questions together so earlier choices inform later ones, reading student-generated figures with a vision model, loosening a synthesized rubric to admit paths the reference never took, and treating injection defense as one stage of a deployed workflow rather than a problem studied on its own. III. S YSTEM DESIGN 

As Section I set out, the grader must handle mixed notebook evidence, score dependent questions together, and credit valid paths the reference did not take. Deployment adds a fourth requirement: harden untrusted submissions, keep an instructor in the loop, and ship scores through the course LMS. We walk the pipeline below, returning to Figure 1.

C. Parsing Notebook Evidence 

Parsing turns a flat cell sequence into typed evidence per question, so later stages see prose, code, output, and figures as labeled objects rather than one undifferentiated document. For each question the parser stores the question ID, mark-down, code, and captured output, figures included. Notebook cells share one execution state, so a captured output reflects everything run above it; keeping outputs as submitted pre-serves the student’s execution trace that grading is later judged against. In the running example, Q1 holds the feature-choice rationale, Q2 the retraining code with the error metric it printed and the plot it drew, and Q3 the comparison write-up. Each question also carries a type tag naming the evidence to expect: code (source and execution results), plot (a generated figure and its visual properties), analysis (ex-planatory reasoning), open-ended (justified interpretation or design choice), exact (a specific value or string), and mixed 

(multiple types, the default). The running example uses three: Q1 is analysis , grading a justification rather than an output; Q2 is mixed , producing code, a metric, and a figure at once; and Q3 is open-ended , since many interpretations are defensible and which is correct depends on Q1 and Q2. The tags feed both rubric generation and grading. 

D. Rubric Generation and Softening 

Rubric generation starts from the instructor’s reference solution but has to produce something assignment-specific rather than implementation-specific. For the running example, that means credit for a reasonable feature-removal rationale in Q1, a correct retraining procedure and accurate error reporting in Q2, and a Q3 comparison consistent with whichever feature the student actually dropped. One model call per question group produces the rubric, using a structured-output schema [17]. The prompt combines a rubric-authoring instruction, the reference solution for each question in the group, and the question-type instructions. The model returns per question a list of criteria, each with a description and a point deduction. Point totals are fixed by the assignment; deductions must sum to the total, and the pipeline rescales them when they do not. Deductions from a fixed total keep the model from inflat-ing point values, but push rubrics toward enumerable faults. Open-ended items such as Q3 suffer most, since their failure modes are harder to list than those of a retraining procedure. Section V returns to this. A softening pass makes a second call that keeps the criteria and point allocations but generalizes anything tied to the reference implementation. Criteria drawn from the reference tend to demand the specific thing the reference did: remove the number of bedrooms, preprocess with StandardScaler ,report this error value. Softening rewrites them to accept any coherently justified feature choice, any equivalent preprocess-ing, and results consistent with the student’s own run. The pass runs by default and can be turned off per assignment. Rubric review is the first instructor checkpoint (Figure 2). Staff inspect and edit the softened rubric before any grading call, and the final rubric hash is stored with every graded question so feedback traces back to the exact rubric used. 

E. Rubric-Guided Grading 

Each student is graded separately, and each question group is evaluated in one model call containing every question in it, so the model sees dependent questions together and can weigh later work against the student’s earlier choices instead of treating each answer as self-contained. Grouping trades context against prompt size: a group has to be large enough to hold the dependencies and small enough that the model attends to each question, so instructors group questions that share a data or modeling decision, typically two to four. Each prompt pairs the student’s evidence with the match-ing rubric. That evidence is student-authored and therefore untrusted, so it is sanitized and wrapped in delimiters the student cannot forge before it enters the prompt (Section III-F). The reference solution is left out by default, since the rubric already carries the expected behavior; including it would push the model toward reproducing one implementation when other paths are valid. Where a question includes plots, as Q2 does, a vision-capable model receives the figures as images alongside the markdown, code, and captured output. The model returns, per question, a score, feedback tied to rubric criteria, a confidence level (low, medium, or high), and a requires_review flag, all under a structured-output schema [17]. This avoids extracting scores from free-form text [11]. Invalid or incomplete output is retried a bounded number of times; when retries run out the question is flagged 

requires_review rather than dropped. Grouping is what lets the grader catch a student who justifies removing the number of bedrooms in Q1 but drops Fig. 3: Instructor Review tab. Staff can move through ques-tions, inspect rendered notebook evidence, review rubric feed-back, and save or regrade before exporting to Gradescope. floor area in Q2, credit an unconventional but defensible Q1 choice carried correctly through Q2 and Q3, and count a mistake propagated consistently across the three questions once rather than three times, the way a human grader would. An autograder seeing Q2 alone can ask only whether some model was retrained and some error reported. Results are saved incrementally, so an interrupted run re-sumes without regrading finished submissions. Each graded question records the model, rubric hash, and timestamp, and the run summary aggregates token usage. 

F. Safety Guardrails 

Students write the text the grader reads. In the running example, Q1 and Q3 are free-form markdown a student could use to address the model directly. The system therefore defends on both sides of the call. Before the prompt goes out, student text is delimited, Unicode normalized, and format, control, and bidirectional characters used in stealth injection stripped; student copies of the boundary markers are replaced with inert characters so a submission cannot forge the structure the grader depends on. After the response, output is constrained to a fixed JSON schema and scores clamped to the valid range, so a payload that survives sanitization and sways the model still cannot yield a malformed or out-of-range grade. Detected stealth Unicode sets requires_review . Section IV-F tests these defenses on a synthetic HW2 red-team benchmark. 

G. Instructor Review and Export 

Review is the second instructor checkpoint, and no score reaches a student without passing through it. Staff see a stu-dent queue, per-question navigation, parsed evidence, rubric-grounded scores and feedback, model confidence, and review flags (Figure 3), and can edit or regrade individual questions before release. The confidence labels keep the checkpoint tractable at class scale: low-confidence Q3 scores can be triaged first, since open-ended interpretation is where the grader is least reliable. After review, the system exports an Excel workbook and a Gradescope autograder ZIP, published once the instructor uploads it and releases grades. IV. D EPLOYMENT AND EVALUATION 

We evaluate the system in two settings. In the live deploy-ment, it graded four notebook assessments in a Spring 2026 machine learning course. For agreement evidence beyond one cohort, we also re-graded 171 archived submissions from nine lab assessments spanning Spring 2024–Spring 2026 and compared totals with the original teaching-staff scores. We analyze run-to-run stability, human-score agreement, student reception, operational cost, and a prompt-injection stress test. 

Ethics and anonymization. We use two datasets: a live deployment, which graded work for credit, and a retrospective comparison of assignments already graded manually. Students in the live deployment were told grading was AI-assisted, and instructors reviewed every score before release. Retrospective scores affected no student. All data were de-identified before model comparisons or aggregate reporting.

E. Cost and Efficiency 

From the five-run HW1 study (Table I), per-student costs ranged from approximately $0.02 to $0.16 per run, with full-cohort runtime between 1 m 21 s and 5 m 12 s for 23 students. Using gpt-4.1 , one class-wide run cost approximately $2.41 and five runs $12.07, against an instructor estimate of around 10 hours to grade the same assignment and cohort by hand. That estimate excludes rubric design; rubric review took a further 15–30 minutes per assignment.

Deployment implications. Rubric-guided grading of flow-structured notebooks proved practical for course deployment under three conditions: a curated rubric, low-temperature in-ference, and instructor review before release. Omitting any condition compromised reliability; the contribution is the components’ effective integration under these constraints. 

Model choice outweighed pipeline design. Using the same pipeline, gpt-4.1 reproduced identical total scores for 65.2% of students versus 13.0% for gpt-5 , largely reflecting zero-temperature support rather than overall capa-bility. Model choice also determined injection resistance, with 

gpt-4.1-mini failing attacks resisted by gpt-4.1 . Thus, grading models should be selected based on inference stability and adversarial robustness rather than benchmark performance. 

Softening improved consistency; open-ended items re-mained challenging. Rubric softening generalized reference-specific criteria, allowing equivalent plotting, encoding, and preprocessing choices to receive credit. Open-ended inter-pretation questions remained the main source of uncertainty because valid responses cannot be exhaustively captured by deduction-based rubrics, consistent with prior work [9], [12]. 

Cost versus instructor time. Class-wide gpt-4.1 grading cost about $2.41, versus an estimated 10 hours of manual grading plus 15–30 minutes of rubric review. Overall benefit still depends on instructor review time for flagged results. 

Independent failure modes of defense layers. Although 

gpt-4.1-mini was influenced by the payload, schema constraints and score clamping still enforced a valid, in-range grade. The outcome was a grading error rather than a com-promised pipeline, preserving the intended layered protection. 

Limitations. This single-site study covers one course, one instructor team, and 24 students. Run-to-run stability across four models from one provider may not generalize to other vendors. Agreement evidence combines a 130-pair HW1 com-parison with archival lab scores from different terms and grading practices, so it is descriptive rather than a unified benchmark. Human graders were also the system’s authors, though archival staff grading partially mitigates this. Student feedback came from 7 of 24 respondents. 

Outlook. Next steps are replication across courses and institutions, other model providers, agreement by question type, and measured instructor review time. As it stands, flow-structured notebook autograding is workable at small-class scale today with a curated rubric, a model supporting low-temperature inference, and a human checkpoint before release.

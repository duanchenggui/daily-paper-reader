# Explain Your Code: AI-Based Examination at Class Scale 

David Sarne a, Shachar Sagi a, Yossi Ben Zion b, ∗

> aDepartment of Computer Science, Bar-Ilan University, Ramat Gan, 5290002, Israel
> bDepartment of Physics, Bar-Ilan University, Ramat Gan, 5290002, Israel

Abstract 

Generative AI has weakened the link between working code and a student’s understanding of it. Oral examination, the traditional test of that under-standing, does not scale to large courses. We report the full-course deploy-ment of a three-agent AI system that examines students on their own code. The first, the examiner, asks three questions anchored to specific lines of the submission, adapting difficulty to each answer, in a 16-minute text dialogue. The other two grade: a code reviewer that never sees the examination and a grader without direct access to the code. Authorship is assessed separately and is advisory. The system examined 247 students in an operating sys-tems course (three exercises, 546 sittings, two examination languages). The grader’s oral score was uncorrelated with the same submission’s code quality score (Spearman ρ = −0.073, 95% CI [ −0.205, 0.063], n = 216) yet tracked degree grade point average ( ρ = 0.419, [0.294, 0.523], n = 214), while auto-mated test scores sat at the ceiling. The mean of a student’s two oral scores correlated with grade point average at 0.468 ([0.353, 0.568], n = 210), within the range of grades in three single-semester courses built on programming assignments. Model spend averaged at most $1.37 per sitting. In surveys, students began skeptical of the AI examination and rated it more favorably after sitting it twice. These results indicate that examining students on their own code is feasible at class scale, and that its score relates to academic standing where the code quality score does not.

1. Introduction 

By students’ own accounts, generative AI is now a routine part of produc-ing assessed work: in successive surveys of UK undergraduates, 88% in 2025 and 94% in 2026 reported using it to help with their assessments (Freeman, 2025; Stephenson and Armstrong, 2026). In programming, where a language model can produce a working solution from a prompt in seconds, a passing submission stops being clear evidence that the student who handed it in can do the work. Computer science undergraduates have been observed describ-ing a task to a model, checking that the returned code runs and submitting it, without working through the errors and revisions that build understanding (Hak et al., 2025). In a randomized experiment with developers learning an unfamiliar Python library, AI assistance impaired conceptual understanding, code reading and debugging without significant efficiency gains on average (Shen and Tamkin, 2026). The cost does not fall on all students equally. Novices who did not struggle used generative AI to accelerate work they had already intended to write, while those who struggled finished with an illusion of competence (Prather et al., 2024). The change is visible in what students submit as well. On a single assignment left unchanged for five years, students after the release of ChatGPT changed more code between consecutive sub-missions but gained less score from each, which the authors read as a loss of both productivity and learning (Zhang et al., 2026). The gap predates gener-ative AI: about a third of introductory students whose programs passed the automated tests struggled to explain their own code (Lehtinen et al., 2021a). Assessment that reads only the artifact therefore rests on an inference, from working code to understanding, that these findings put in doubt. One response is the oral examination, in which a student defends their work live with no tools at hand. It is both used and advocated as an in-tegrity response: institutional guidance routes suspect submissions to it, and researchers argue that written assessment may need replacing with face-to-face forms (Kofinas et al., 2025). A human oral defense for every student in a large course, however, is expensive, and hard to keep consistent across graders. An automated system deployed in an undergraduate artificial in-telligence and machine learning course at NYU Stern, across cohorts of 36 and 37 students, shows that AI can conduct oral assessment at very low 2cost (Ipeirotis and Rizakos, 2026). Its authors also report that the model panel graded more strictly than human evaluators and agreed poorly until a consultation step. That system questions the student from an instructor rubric and a text description of the project rather than from the submitted artifact. Section 2 reviews three lines of prior work: systems that ask ques-tions anchored to a student’s own code but do not examine, systems that examine autonomously and adaptively but do not read the submission, and designs that combine the two but have been described without participants or deployment (Church et al., 2025; Vintila, 2024; Frankford et al., 2026). To our knowledge, questioning from the submitted code and autonomous examination have not been brought together in a running course. We report on ATC, the Autonomous Testing Center, an automated ex-amination system for programming assignments that examines each student autonomously on their own submitted code. The system is built from three agents, each a large language model given its own instructions and its own inputs. The first, the examiner, reads the student’s own submitted code and questions the student on it. Its questions are anchored to specific lines of the code and adapt in difficulty to each answer, and it scores each answer as it is given, which guides the difficulty of the next question. The second, the Code Reviewer, sees the code but not the examination, and produces a code quality score. The third, the Grader, scores the examination as a whole from its transcript, without direct access to the code, and produces an oral score. The final grade combines the oral score and the code quality score by fixed arithmetic. Understanding and authorship, meaning whether the stu-dent appears to have written the code, are kept as separate axes, so that a nervous but genuine student is not treated as an impostor. The examination is conducted in text: the student reads the questions on screen and answers in writing. We keep the term oral, as is usual for an examination in which a student defends their own work in dialogue, although every answer here was typed. We chose text because a typed answer lets a student organize an ex-planation of code and revise it before submitting it, and it avoids transcribing identifiers and technical vocabulary from speech. We deployed the system on the Introduction to Operating Systems course at Bar-Ilan University, in two examination languages (Hebrew and English). Figure 1 shows the process from the student’s side. Our aim is feasibility rather than efficacy: we ask whether such a system can run on a full course at the cost we report in Section 5.9 and produce grades that relate to other measures as the design predicts. Before any examination data were extracted for analysis, we fixed five success cri-teria, each with a numeric threshold: three on the examination scores and two on the automated test scores. We report the outcome of each, and a criterion that failed is reported as a finding rather than revised after the fact. Analyses that were not pre-specified are reported as exploratory. We do not claim that these grades are validated against human examiners. That comparison is left to future work. This paper makes four contributions. First, submission-aware question-ing inside an examination. The questions are generated from the student’s own code and anchored to specific lines, rather than to a rubric or a project summary. They are asked adaptively in dialogue, and the examination pro-duces a grade of record, one that counts toward the course grade. Second, a three-agent assessment design in which each agent sees only part of the evi-dence. The code review is kept apart from the examination, their scores are combined arithmetically, and understanding and authorship are scored inde-pendently. The examiner also carries fairness and safety behaviors: a distress path that ends the examination when a student signals distress, handling of instructions planted in an answer to manipulate the examiner (prompt in-jection), explicit rules against penalizing trivial slips, and a complaint flow for a student shown code that is not theirs. The distress path, the injection flag and the complaint flow were in place throughout, but were not triggered during the deployment. Third, a deployment at full class scale, across three exercises in two examination languages, at an average model cost of at most 4$1.37 per sitting (Section 5.9). Fourth, empirical observations against cri-teria fixed in advance. The oral score is uncorrelated with the code quality score of the same submission while tracking degree grade point average. The automated test scores sit at a ceiling, which leaves no room to detect whether students who expected automatic grading wrote their code differently. An exploratory comparison places two short oral examinations, as an indicator of academic standing, within the range of grades in single-semester courses that, like this one, are built on programming assignments. 

2. Related work 

The previous section argued that a working submission is weak evidence of student understanding, and that oral examination is the response the integrity literature reaches for. In an oral defense, the examiner questions the student on the work they handed in and follows up on each answer. This section therefore asks which of the systems built to put that response into software have two properties, one for what is asked and one for how. The first is that the questions come from the student’s own submission, rather than from a rubric, a project description or the course materials, so that they test the student’s account of it. The second is that the system itself conducts an adaptive dialogue about that work, rather than issuing fixed items or handing questions to a human examiner. Only a dialogue can pursue a weak answer, and only one conducted without an examiner can run at scale. How far each system has been deployed is stated in Table 1 but is not used to sort the systems. Assessment of programming assignments has mostly rested on a different instrument: automatic execution of the submitted program against test cases, which has been surveyed as a field in its own right (Douce et al., 2005) and as part of automated assessment more broadly (Paiva et al., 2022). The grade a test-based system produces varies with the test suite used (Clegg et al., 2020). Because such tests check only what a program outputs, assessment that also examines the code itself has been proposed (Jin and Charpentier, 2020), and the strengths and limitations of existing systems have been reviewed (Ullah et al., 2018). Section 5 reports a ceiling in this instrument’s scores in the present deployment. Oral examination in computing is also more than an integrity response. It has been studied as an assessment method in its own right: in introductory computer science (Ohmann, 2019), in software courses at several institutions 5(Ohmann and Novak, 2025), and as interviews on individual take-home pro-gramming assignments (Kannam et al., 2025). In an introductory course of 628 students, 21 staff gave each student two five-minute oral examinations, at a cost of about 180 staff hours (Ellis et al., 2026). Motallebi et al. (2026) map this work systematically for computing. In all of these studies people conduct the examination, which is why they are not in Table 1. The idea of asking students automatically generated questions about their own programs was introduced by Lehtinen et al. (2021b). Lehtinen et al. (2023) generate multiple-choice questions from the submitted Python pro-gram by static analysis, citing literal line numbers and drawing distractors from the student’s own identifiers. Caniço and Santos (2025) instantiate templates with the submission’s structure, identifiers and execution data, so that a question names the student’s own functions and variables, and describe their deployment as preliminary. Goodfellow et al. (2026) use generative AI to produce multiple-choice questions from each student’s submitted code and restrict them to formative use. Anchoring a question to the student’s own code, and to a specific line of it, is therefore not new. What these systems lack is an examination: a sequence of questions that responds to the student’s answers and ends in a grade. Another line conducts the examination but does not start from the stu-dent’s submission. Ipeirotis and Rizakos (2026) deploy a voice agent that examines students from a rubric and a text description of the project, as a replacement for the final examination. Socratic Mind (Hung et al., 2024) opens with instructor-defined questions and adapts its follow-ups to the stu-dent’s answers. Instructors configure the prompts, the desired answers and the rubrics, and a feature drafts questions from lecture materials. Where code is discussed, the instructor supplies it. A later study of the same sys-tem (Lee et al., 2026) reports an optional extra-credit assignment, formative rather than an assessment of record, in a mixed text and voice interface. Au-tonomous adaptive examination of a real cohort is therefore not new either. What these systems do not do is read what the student handed in. How the examination is graded differs too. Ipeirotis and Rizakos (2026) use a panel of language models that score the same material, followed by a consultation step between them, a method also proposed for evaluation beyond education (Verga et al., 2024). Agreement among their models was poor before that step, and after it about 60% of ratings fell within one point of one another and 29% matched exactly. Three published designs have both properties. Church et al. TAMIGO (Anishka et al., 2024) comes close without having both properties: it generates oral examination questions from course materials and assignment descriptions, and teaching assistants administer them, so the system never questions a student. These three designs describe the conjunction of the two properties, but to our knowledge none has been used to examine students in a course. The gap, then, is that the two properties have not been brought together in a running course. ATC is a deployed instance of that conjunction, produc-ing a grade of record per assignment across a term on a full undergraduate cohort. None of its parts is claimed as new: the anchoring belongs to the line on questions about learners’ code, the autonomous adaptive dialogue to Ipeirotis and Rizakos and to Socratic Mind, and the architecture that joins them to Church et al., to Vintila, and to Frankford et al. What was missing was evidence about what such a system does when it is run on a real course at scale, which Section 5 reports. 83. ATC system design 

3.1. Design goals 

The system was built to answer one question at the scale of a full course: does this student understand the code they submitted? Three commitments follow from that question. The first is that questions must be anchored in the student’s own submis-sion rather than in course material or a description of the work. A question that can be answered from the assignment brief, from generic operating sys-tems theory, or from an explanation of the code the student read shortly before the exam does not separate understanding from recall. The second is that the assessment must not require a human examiner in the loop, because a human oral defense for every student on every assignment is the cost that made oral assessment rare (Ellis et al., 2026). The third is that the resulting grade must be defensible after the fact. This means structured output, a full audit trail, and a grading path whose arithmetic a student or an appeals committee can follow step by step, rather than a single holistic judgment by a model. One further commitment is that the grade is not meant to depend on whether AI was used. The system records an advisory signal of machine-generated style for staff (Section 3.5), which never enters the arithmetic that forms the grade and is not validated here as a detector. Students were permitted to use AI assistants, and a student who used one and can explain every decision scores well. This section describes the system as configured for the deployment re-ported in Section 4. Figure 2 summarizes how an examination runs and how it is graded, and Appendix A gives the implementation detail an adopter would need.

3.3. Code-anchored adaptive questioning 

Each exam consists of three questions and allows 960 seconds (16 min-utes), extended to 1140 seconds (19 minutes) for students entitled to extra time, as described in Section 3.6. The clock stops while the examiner gen-erates the next question, so the time a student waits for the model does not count against the allowance. Questions are asked and answered in text. The interface is a split screen with the submitted code on one side and the dialogue on the other (Figure 3). Each question together with the student’s answer to it is called a turn. Questions are generated during the examination from topics. Each assign-10 ment has a topic pool, built before the assignment opens. Once per course, staff set the conceptual dimensions that suit the subject. For operating sys-tems these are design choice, edge case, error handling, interface depth, code flow, and cross-file interaction. For each assignment, the system then gener-ates topics automatically from the assignment, and the course staff remove those that are unfair at that point in the semester, that the assignment did not require, that can be answered from the instructions alone, or that cannot be answered in about five minutes. A topic is the basis for a question and contains no question text. It speci-fies the files it targets, a focus, one of the dimensions, a difficulty label, a note telling the examiner what to probe, and the topics it must not be combined with in one exam. One topic, for example, targets tournament.c , with the focus “the fork() call that creates four child processes”, the dimension error handling and the difficulty medium. Its note asks the examiner to have the student show where the processes are split, and to check whether the code tests the return value of fork() for failure. Which topics are offered is de-cided by deterministic code with no language model, which spreads questions across files and dimensions and excludes repeats and conflicting topics. The examiner receives the student’s code together with a small menu of these topics, and a topic becomes a question only when the examiner meets it with that code: the examiner formulates the question from the code itself, quoting the student’s identifiers and referring to specific lines. The same topic can therefore take many forms, even on the same code. The examiner can also direct the interface to scroll to and highlight a specific file and line, so the student can see the code being asked about. It may also change the condi-tions of a question, asking what the code would do with a different input, or propose a change to the code and ask how its behavior would differ. If the examiner notices a flaw in the code, it may set the planned topic aside and ask the student to explain that flaw instead. The exact wording of a question therefore cannot be known in advance, and a student prepares by studying their own code. Figure 4 shows an example exchange. Difficulty adapts within the exam, over three levels: easy, medium and hard. The first question is chosen between two topics of medium difficulty. After each answer the examiner records an understanding score from 1 to 5. For each of the two later questions it then receives two topics at each level and chooses the level it judges the next question should have, guided by a stepping rule: a score of at least 4 steps up one level, a score of at most 2.5 steps down one level, and intermediate scores hold the current level. 13 3.4. Three-agent grading with separated inputs 

Grading involves the three agents introduced in Section 1. The examiner records a score for each answer during the exam (Section 3.3). After the exam ends, the Code Reviewer and the Grader work from separated inputs, and their scores are then combined by arithmetic. The Code Reviewer sees the assignment description and the submitted source code and has no access to the exam transcript. It produces the code quality score, feedback for the student, notes for staff, and a structured as-sessment of how machine-generated the code’s style looks, which is discussed in Section 3.5. The Grader sees the assignment description and the full transcript, together with that style assessment, and has no direct access to the submitted code. It re-evaluates the understanding scores the examiner recorded for each turn and may override them. It then produces the oral score from two quantities, the average of those scores and the difficulty of the questions the student answered, as described below, and writes both stu-dent feedback and a staff report. The combination step is arithmetic: the final grade is 0.75 times the oral score plus 0.25 times the code quality score, rounded to the nearest integer, with no caps and no penalties applied to it. Sittings that reach the time limit are graded on the partial transcript, with the Grader told which questions were answered and which were never reached. The separation is central to the design. If one agent saw both the code and the transcript, clean code would flatter the oral score and a fluent defense would flatter the code quality score, and the two numbers we most want to compare would be formed from the same evidence. Even so, three routes carry code-derived information to the Grader: the lines the examiner quoted, the per-turn scores recorded by an examiner that had read the code, and the style assessment. Section 6 considers what they imply. Keeping the two inputs separate is what makes the result in Section 5 meaningful, and it is also why the two scores are combined by a formula rather than by a further model judgment. 

Scoring rules and models. On the examiner’s understanding scale, a 5 is an answer that explains both what the student’s code does and why, in terms of the underlying operating systems mechanism and specific to that code. A 3 is an answer that describes what the code does without explaining why. A 1 is an answer that cannot explain the code or contradicts it. Forgetting an exact string or a variable name, or answering correctly at a higher level of 14 abstraction, does not bring a score below 4. The Grader then re-scores every answer from the transcript on the same scale, with its own rules and with the instruction to favor the student where an answer is ambiguous and to grade the answer the student gave rather than the fuller answer the model might have preferred. A short answer that is correct scores at least 3, and scores of 2 or below are reserved for answers that are wrong or incoherent. The Grader forms the oral score in two steps. In the first, a fixed table gives a range of oral scores from two inputs: the Grader’s understanding scores for the student’s answers, divided into seven bands, and the difficulty profile of the questions the student answered, one of three: at least one hard question, medium questions only, or at least one easy question. All but one of the ranges are five to fourteen points wide, the exception being the lowest band with an easy question, which runs from 0 to 38. Within a band the three ranges overlap, and a harder profile receives a higher range. Between bands, ranges overlap down to a mean of 2.5 and touch or leave a gap below it. In the second step, the Grader places the student within that range by its judgment of the answers, except when fewer than three answers could be graded, in which case it places the student at the bottom of the range. Figure 4 gives an example. The Code Reviewer assigns a score from a table of six tiers. Each tier is described jointly by coverage, meaning which required files and features are present, and by correctness, meaning how far the code that is present implements the specification, judged by reading it, including whether system call return values are checked and memory is freed. A missing required file costs between 10 and 15 points, and where a submission falls between two tiers the higher one is taken. The agents ran on Claude Opus 4.6, called through the provider’s appli-cation programming interface, with their output forced into a fixed schema (Appendix A). When Opus returned no answer, a call fell back to Claude Sonnet 4.6 and then, as a last resort, to a Gemini model from Google, so that an exam in progress would continue instead of failing. The Grader and the Code Reviewer ran at temperature 0.1, and the examiner at a temperature drawn for each sitting between 0.2 and 0.4 and stored with it. 

3.5. Authorship as a separate and advisory axis 

Understanding and authorship are kept on separate axes. During the exam the examiner rates each answer for authorship confidence, that is, how 15 confident it is that the student wrote the code (high, medium, or low), in-dependently of whether the answer was correct. The question behind this rating is whether the student speaks about the code as its author, referring to implementation details that only someone who worked on it would know, as opposed to reciting general theory that fits any submission. A student who defends their own design choice wrongly but with such details therefore receives a low understanding score but is still rated as the likely author. This per-turn rating is the primary signal. A second, supporting signal is the Code Reviewer’s style assessment, which looks for stylistic markers of machine-generated code and returns a level from 0 to 3 with an explanation. It cannot by itself produce an adverse authorship finding. The two signals are combined through a fixed table into one of three outcomes: authorship established, partially established, or not established. After the exam the Grader can also raise a flag, called an integrity flag in the system, when a student consistently fails to explain their own code. Despite its name, the flag concerns understanding rather than authorship, and the same rule applied in every sitting. The authorship outcome and the flag are shown to staff for human review, and neither enters the grade. An automated pipeline should not convict a student of misconduct, so concerns are routed to people. Two staff reports from the deployment show the two axes apart. In the first, the Code Reviewer found strong signs of machine-generated code, the same pattern repeated across four files with no traces of development. In the examination, however, the student explained why standard input is a stream that can be read only once and walked through a six-stage shell pipeline step by step. The system gave an oral score of 92 and recorded authorship as established. In the second, the answers themselves pointed away from authorship: the student could not explain a break statement in a loop of their own script, claimed that the loop kept running, contrary to the submitted code, and then asked to switch the question, saying they had not written that line. The system gave an oral score of 69, recorded authorship as not established, and passed the case to staff. 

3.6. Safety and fairness rules 

Emotional distress is handled as an expected case. The system has no view of the student beyond the text they type, so what it acts on is what the student writes: a message stating or plainly conveying that they are 16 panicking, that they are crying, or that they cannot continue. On such a message the examiner ends the exam immediately and gently, the session is marked accordingly, and no grade is computed. A teaching assistant is notified with the triggering message and a link to the transcript, and the student is exempted from the lock that otherwise prevents a further attempt without staff action (Section 4.5), so that a fresh session can be arranged. The trigger criteria are strict, so that the ordinary frustration of an examination does not end a graded sitting: frustration, tiredness, saying “I don’t know”, or calling a question unfair do not qualify. Adversarial input is handled without changing the examiner’s tone. In-structions planted in an answer to redirect the examiner are ignored in the dialogue, flagged in the structured output, and reported to the Grader and to staff, and the flag alone does not change the score. Hostile or coercive de-mands are declined in a scripted, even-handed way and recorded verbatim. Students who believe the displayed code is not theirs can say so during the exam. The complaint is recorded with full session metadata, staff are emailed, the exam ends on an acknowledgment screen, and the account is locked so that no new exam can start until a human has reviewed the case, with the transcript preserved for that review. Section 5.1 reports how these provisions behaved in testing and during the deployment. Two further provisions concern access rather than conduct. Exams run in either of two languages, selected by the student before the session begins: Hebrew, the language of instruction, which is the default, or English. The examiner instructions are maintained separately for each language instead of being translated at run time, so that the examination assesses understanding of the code rather than command of academic English. Students entitled to extended time are identified automatically from a list supplied by the course, with no manual step per session, so they do not have to disclose the accommodation at the examination.

4.2. The crossover design, and what varied 

Two lecture groups were opened for the course, and students registered to whichever they chose, forming the groups denoted S with 84 students and L with 163. The groups sat the same exercises on the same schedule. On exercises 1 and 2 they differed in what they were told in advance about how their work would be graded. On exercise 1, group S was told that the exercise would be graded by the AI examination system, and group L that it would be graded by the course’s automatic tests, which run the submitted program against fixed test cases (Section 4.4). On exercise 2 the two groups swapped, and on exercise 3 the whole cohort was told it would be graded by the AI examination system. We call the two conditions arms, although the groups were not randomized. We name them told-AI and told-autograde, because the distinction concerns what the student knew when writing the code rather than which score was computed. Table 2 summarizes the design. The order followed a gradual rollout, chosen to reduce the risk of a first deployment of a new system: the oral examination was introduced for one group on exercise 1, moved to the other group on exercise 2, and used for the whole cohort on exercise 3. Because the order was reversed between 18 the groups, every student was assigned one told-AI exercise and one told-autograde exercise on exercises 1 and 2. This supports a comparison, on each exercise, of how the two modes were received and of how automated test scores behaved under each incentive. It does not support a comparison of learning or of grade quality, because mode is tied to exercise content within each group, and the groups differ in size and in track composition. Section 5 reports the reception and incentive comparisons on that basis and reports nothing about relative attainment across modes.

4.5. Procedure Submission intake. The system fetched each submission from the student’s repository at examination time (Section 3.2), so there was no separate up-load step. Students could not change their repositories after the submission deadline, which ensured that the code examined was the code they had sub-mitted. 

Booking, examination periods and retakes. After submitting, each student booked an examination slot through an online calendar, and a reminder was sent automatically the day before the slot. 20 Each exercise opened with a booking window of three weeks, announced to students as the period within which they were expected to sit. The window was not enforced as a deadline. A student who had not booked within it, or who had booked and not attended, could sit afterwards on request, and every such request was granted by a member of the teaching staff. On every exercise, sittings arising from extended absences were still taking place well after the window had closed. A per-account lock prevented a student from starting a further sitting on the same exercise without staff action. All students were told that a further attempt could be requested, and the grade of the last sitting counted for the course. A student seeking a further attempt asked the teaching assistant, who authorized it in the system and reports granting every such request. In practice this happened in two situations: after a technical problem during the examination, which leaves no grade, or when the student was dissatisfied with the grade received. Staff usually permitted the further attempt by invalidating the earlier sitting, whose record was retained rather than deleted. Where a student sat more than one sitting on the same exercise, the analyses that test the success criteria use the sitting that first produced a grade, and the later sittings are reported descriptively in Section 5.1. 

The examination environment. Examinations took place in person, in a ded-icated room in the computer science building, and the room was unattended: no invigilator was present at any point, and the door was left unlocked. Each student sat at a workstation running in locked-down kiosk mode, which blocked external applications and browser access, and left personal belong-ings in a designated corner of the room. Students had the teaching assis-tant’s email address and telephone number for any problem during a sitting. Two cameras recorded continuously, and the course instructor reviewed the recordings by sampling, partly live and partly on the following day. Sam-pling covered on average five minutes of each hour of recording, viewed at double speed, and checked that the student was alone, that belongings were in the designated corner, and that no phone or personal computer was in use. The cameras’ built-in person detection, which runs on the device, tagged the intervals in which a person was present, so the sampled minutes fell on occu-pied time. Beyond that tagging, the footage received no automated analysis. An hour of recording spans roughly three sittings, so no sitting was reviewed as a matter of course, but every sitting had a chance of being observed. The review found no violation in any sitting it covered. 21 Unlike the self-recorded setting reported by Ipeirotis and Rizakos (2026), in which students sat the examination on their own machines wherever they chose, here the machine and the room were controlled. In both cases the sitting was recorded and no member of staff was in the room. The room is a property of this deployment rather than of the software. A course adopting the system without a controlled room would obtain the same questioning and grading behavior, with weaker guarantees about the conditions in which answers were produced. 

Appeals. Every grade could be contested before a human. A student who disputed a grade could appeal by email within a week of receiving it, stating the grounds, and staff sent the transcript of the sitting on request. Appeals were decided by the teaching assistants after the examination period, by reading the transcript and the code. An accepted appeal corrected the course grade rather than the stored result, and every figure in this paper is the system’s own grade before appeal. We analyze the stored grades because the object of study is what the system produced and because an appeal adds a human judgment only for the students who chose to appeal. Section 5.1 reports how many appeals were filed and how they were decided. 

Surveys. Before each exercise was graded, students received an email telling them how the exercise would be graded (by the AI examination system or by the course’s automatic tests), with a link to a short course-evaluation form about that mode. After each AI examination, a second form was sent with the grade and the written feedback, because several of its items ask about the grade and the feedback received. The surveys were mandatory, but completion could not be enforced. Appendix D gives the three forms, and Section 5.8 reports the results. 

4.6. Consent, ethics and data handling 

The examinations and surveys were part of the course’s regular assess-ment and evaluation. Students were told in advance that an AI model would examine them and that the examination room was recorded. The surveys were designed to improve the system and to report on its use to the univer-sity rather than as research instruments. The analyses reported in this paper were conducted on data generated by that assessment, with no additional re-search procedure imposed on students. Research use of the existing data was approved retrospectively by the Human Subjects Institutional Review Board 22 of Bar-Ilan University (approval number 0109261257, 1 September 2026), which waived individual consent because the data were anonymized before analysis. The approval covers the examination records, the survey responses, degree grade point average and the course grades used for comparison in Section 5.7. The camera recordings described in Section 4.5 were not used as research data. Degree grade point average and the course grades were matched to the course data by student identifier immediately before anonymization. The identified version was used only for that matching and was not retained. All analysis was carried out on the anonymized dataset, with session identifiers dropped and free-text survey responses excluded. Under the model provider’s published retention policy, inputs and outputs sent through its application programming interface (the agents’ instructions, the assignment instructions, the files of the student’s submission, the tran-script and the Code Reviewer’s style assessment) are deleted within 30 days by default (Anthropic, 2026), and under its commercial terms they are not used to train its models (Anthropic, 2025). The submitted code, the tran-scripts and the grading reports are kept in the deployment’s own project on Google Cloud Platform (Appendix A), which commits in its data process-ing terms to comply with the General Data Protection Regulation (GDPR) and provides integrated security controls (Google Cloud, 2021). The camera recordings were kept for one week and were accessible only to the course staff. No appeal drew on them, since the full text of every answer and complete logs were available. 

4.7. Success criteria and analysis 

Five success criteria, each with a numeric threshold, were fixed before any examination data had been extracted for analysis. Three concern the oral score and are evaluated on exercise 3, and two concern the automated test scores and are evaluated on exercises 1 and 2. Only these five are confirma-tory. Every other coefficient in this paper is descriptive or exploratory, and Section 5 identifies which. Whether the system could run on the full course, and at what cost, is reported descriptively (Sections 5.1 and 5.9). The three criteria on the oral score apply the discriminant and convergent logic of construct validation (Campbell and Fiske, 1959). If the oral score reflects the student’s account of their own code, it should not simply restate how good that code is, it should relate to how the student stands elsewhere in the degree, and it should relate to that more closely than to the quality of 23 the code. The thresholds follow the conventional benchmarks for correlations, 0.10 for a small and 0.30 for a medium relationship (Cohen, 1988). • S1, discriminant: the upper bound of the interval for the correlation between the oral score and the code quality score is below 0.30, so that the data rule out even a medium positive relationship. With 216 students the interval extends about 0.13 on either side of the estimate, so an observed correlation above about 0.17 would fail S1. • S2, convergent: the lower bound of the interval for the correlation between the oral score and degree grade point average is above 0.10, so that the data rule out a negligible relationship. The threshold is low because grade point average is a coarse criterion (Section 7). • S3, separation, the primary criterion: the interval for the difference between these two correlations lies entirely above zero. This tests the central claim directly. The design predicts the direction, and a negative difference would contradict it. The two criteria on the automated test scores concern the instrument the oral examination was meant to complement. The deployment rested on the premise that the course’s automatic tests discriminate too little between students to carry a grade, and the crossover made it possible to ask whether students who expected automatic grading aimed their code at the tests. • S4, premise: in the told-autograde arm, the automated test scores have a median at or above 90 and an interquartile width at or below 15, on exercises 1 and 2 separately, since their harnesses differ. • S5, incentive: on both exercises, the told-autograde median exceeds the told-AI median, with the interval for the difference excluding zero. The surveys (Section 4.5) also carried ten hypotheses about student at-titudes. They were written after the deployment and before any response was inspected, are not success criteria, and are described with their results in Section 5.8. Exercise 3 is the primary analysis exercise for S1 to S3, because it is the only exercise on which both groups were assigned the AI examination. Almost every student entered it with a graded AI examination on exactly one 24 earlier exercise (211 of the 216, while four had none and one had two), so prior exposure is close to balanced. S4 and S5 rest on the automated test scores of the told-autograde and told-AI arms of exercises 1 and 2 (Section 5.4). The exclusion rule, fixed in advance, is the same on all three exercises and acts on recorded status. A record is excluded for non-submission, for not sitting, or for a sitting ended on the distress path, which leaves 83, 162 and 216 usable records on exercises 1 to 3 (Section 4.3). 1 Sittings in which time ran out are retained. Every usable record carries an oral score and a code quality score. Pairings with grade point average run on 81, 162 and 214 records for exercises 1, 2 and 3 respectively, because grade point average was unavailable for two students, both of whom sat exercises 1 and 3 (Section 4.1). The grade point average does not include the operating systems course itself, so the correlations between the oral score and grade point average need no correction for overlap between the two measures. Rank correlations (Spearman) are the primary statistic throughout, be-cause they are robust to single extreme values and to the bunching of scores near the top of their range, and product-moment correlations (Pearson) are reported in Appendix B as a robustness check. All intervals are bias-corrected and accelerated (BCa) bootstrap confidence intervals from 10,000 resamples of students, except the two for S5 (Section 5.4) and the interval for grad-ing stability, which resamples sittings (Section 5.6). They are at the 95% level unless a multiplicity adjustment is stated, which is the case only for the three primary reception hypotheses in Section 5.8. The pairwise n is stated for every coefficient.

Table 4 describes the four measures on the usable records. The oral score is widely spread on all three exercises, taking 31, 33 and 26 distinct values, with standard deviations of 12.55 on exercise 1, 12.57 on exercise 2 and 8.79 on exercise 3. It therefore separates students rather than placing them in a single passing band. The code quality scores are narrower on every exercise, with standard deviations between 4.9 and 7.5 and between 12 and 17 distinct values. They are produced by an agent that reviews the submitted code and never sees the examination, and code that compiles and meets the brief leaves less room to differentiate students than their account of it does. The automated test scores of the same submissions are even narrower, with standard deviations of 1.87 and 2.31, seven distinct values on each exercise, and 98.8% and 99.4% of students at or above 90. The oral score on exercise 3 is compressed relative to the other two ex-ercises. Its median is 88 against 80 and 81, and 43.5% of students score at or above 90, against 12.0% and 7.4% on exercises 1 and 2. Its scores still range from 48 to 97, but bunch more tightly at the top. Three explanations are available, and we do not choose between them. First, exercise 3 was the only exercise on which both groups were assigned the AI examination, and for almost all who sat it, it was their second, so almost all came to it with 29 prior exposure to the format. Second, the topic pool for that exercise was narrower: its examinations drew on 20 distinct topics, against 43 and 30 on the other two. Third, exercise 3 was the one exercise without an automatic grader, so the incentives around the submission itself differed. The compres-sion did not remove the relationship that S2 tests: exercise 3 produced the strongest single-exercise correlation with academic standing (Section 5.3).

Consistency of the code quality score. Corrected code quality scores. On the exercise 3 code quality scores corrected for the recurring review error described in Section 5.1, S1 is +0.002 and S3 +0.412, so both keep their verdicts. 

5.6. Reliability of a single examination Grading of a fixed transcript. To measure how much of a score is the grading model’s run-to-run variation, the Grader and, separately, the Code Reviewer 35 were run again five times each on a stratified sample of 50 usable sittings: 15 from exercise 1, 15 from exercise 2 and 20 from exercise 3, drawn evenly from the five quintiles of the oral score within each exercise. Each repeat used the same instructions, model, temperature and inputs that had produced the stored grade, and the Grader received the stored style assessment unchanged. Run to run, the Grader’s oral scores agree closely. Across the 50 sittings the intraclass correlation of the five repeats (one-way, single run) is 0.978, with a bootstrap interval over sittings of [0.963, 0.990]. The pooled within-sitting standard deviation is 1.7 points, and the median range of a sitting’s five scores is 1 point. All five repeats fall within 5 points of one another in 44 of the 50 sittings. Of the 250 repeats, 241 fall within 5 points of the stored score and 149 exactly on it, with a mean difference of 0.0 points. In the six wider sittings, with ranges of 6 to 12 points, a half-point difference in re-scoring a single answer moves the average across a band of the score table. Three of them sit near an oral score of 60. Exercise 3 is the most stable, with a within-sitting standard deviation of 1.0 point, no range above 6 points, and every repeat within 5 points of the stored score. The Code Reviewer is almost deterministic. Across 49 of the same sittings its intraclass correlation is 0.999 and its within-sitting standard deviation 0.3 points. No sitting’s range exceeds 3 points, and every repeat falls within 5 points of the stored score. When both agents vary together, on those 49 sittings, the combined grade has a within-sitting standard deviation of 1.3 points. Run-to-run variation in grading is therefore small compared with the spread of the oral score, whose standard deviation is 8.8 to 12.6 points (Sec-tion 5.2), and it cannot account for the correlations reported in Section 5.3. It measures only the grading of a fixed transcript. A second examination of the same student would bring different questions, drawn and phrased afresh, and different answers, so its outcome could vary more than the grading does. The correlation between two sittings, reported next, bears on that. 

Two examinations of the same student. A student’s two oral scores correlate +0.313 with each other (n = 212, 95% interval [+0.182, +0.432]). The two sittings examined different exercises, a median of three weeks apart. This figure therefore mixes measurement error with real differences in how well a student understood two different submissions, and the data do not separate the two. 5.8. How students evaluated the two modes 

The surveys (Section 4.5) carried ten hypotheses about how students would evaluate the two modes, numbered H1 to H10. Appendix E states each hypothesis with its decision rule and gives the response rates and the full results. Three hypotheses were designated primary and are reported with 98.33% intervals, the 95% level adjusted for three tests (Bonferroni). The other seven are exploratory and are reported with 95% intervals. They concern attitudes rather than learning, grade quality or how well either mode measures understanding. Because only the AI examination had a post-examination form, every comparison between the two modes sets ex-pectations against expectations. All three primary hypotheses are supported. First, before experiencing either mode, students expected the autograder’s grade to reflect their un-derstanding and mastery better than the AI examination’s (H1, the naive expectation gap). The comparison rests on two items worded identically on both pre-examination forms, combined into one composite score, and gives a Cliff’s delta of +0.305 with a 98.33% interval of [+0.093, +0.490], on 103 respondents to the autograder form and 74 to the AI form at exercise 1. Second, students rated the AI examination more positively after the exer-38 cise 3 examination than before it (H3, the exercise-three experience gain), with a matched-pairs rank-biserial correlation of +0.489 [+0.214, +0.699] on 107 complete pairs. Third, support for keeping an AI-based component in grading rose (H4, the retention-support shift). The net switch, the share of students who moved toward keeping such a component minus the share who moved away, is +0.159 [+0.034, +0.273] on 88 pairs. One exploratory result runs the other way. Students meeting the AI examination first, at exercise 1, rated it lower afterwards than they had expected beforehand (H7), at −0.349 with a 95% interval of [ −0.603, −0.064] on 63 pairs. The exercise 3 gain does not repeat for either group at its first encounter with the AI examination, which was exercise 1 for group S and exercise 2 for group L. Appendix E also sets out what qualifies each supported result: H1 is confounded with lecture group, H3 and H4 were answered immediately after a grade from the system, and the students who answered both forms on exercise 3 had higher oral scores.

6. Discussion 

This study asked two questions of a system that examines each student on their own code: whether it can run on a full course, and whether its scores relate to other measures as its design predicts. In this deployment the answer to both is yes. The system examined 247 students in 546 sittings with no examiner in the room, and the oral score it produced was unrelated to the quality of the code it examined while tracking how students stood in the rest of their degree. The subsections below take up what the oral score shows, what the course’s automatic tests could not show, what running the system required, how many sittings a grade should rest on, how students received the examination, and what assessing understanding means when AI use is permitted. 

6.1. What the oral score shows 

The central result of the previous section is a contrast between two scores that the same system computes from the same submission. The code quality 40 score and the oral score rank students differently, and only the oral score is related to how students stand elsewhere in the degree, in every sample in which it was measured (Section 5.3). The scores computed from the submit-ted code alone, by a reviewing agent or by an automatic test harness, showed no consistent relation to academic standing, while the score from asking stu-dents to account for that code did. One reading, which these data do not test, is that where AI assistance is permitted, as it was here, the quality of the code says little about the student who handed it in, while the student’s account of it says more. No human examiner scored these students, so neither instrument was checked against a standard, and what the oral score tracks remains to be established. One may wonder whether the lack of correlation between the two scores, which we call their decorrelation, is an artifact of the architecture. The two scores come from the same system, and their low correlation might reflect how the system splits its own judgment across two axes rather than anything about students. Two features of the design argue against this. First, the two scores are not two slices of one judgment. The Code Reviewer sees the source and never the transcript, the Grader sees the transcript and never receives the code quality score, and the Code Reviewer runs first and receives nothing from the Grader, so neither can adjust its score toward or away from the other’s. Three code-derived routes do reach the Grader (Section 3.4): the lines the examiner quoted in its questions, the per-turn scores recorded by an examiner that had read the code, and the Code Reviewer’s style assessment, which the Grader receives for the authorship decision. The first two would most plausibly pull the oral score toward the code quality score. The two scores relate to the third in opposite directions (Section 5.5), so it could push their correlation down. With that signal held constant, however, the correlation stays near zero on all three exercises (Appendix B). Second, the decorrelation does not stand alone. The oral score converges with degree grade point average, a measure produced entirely outside the system, over courses it never saw, and a split of the system’s own judgment would not by itself produce that convergence. A grader that rewarded features of the writing that also go with academic standing, such as length or fluency, could. In our analysis, answer length was measured and accounts for only a small part of the convergence (Section 5.5). Taken together, these checks leave the decorrelation standing. 41 6.2. What automated tests can carry 

The automated test scores show no consistent relation to academic stand-ing because their distributions have so little spread that the instrument barely separates students. The weak and inconsistent correlations there are there-fore a property of its variance rather than evidence of independence (Sec-tion 5.4). The same saturation is the main reason S5 could not detect a dif-ference. S5 asked whether students who expected automatic grading aimed their code at the tests, and so scored higher on them than students who expected the AI examination. Half or more of every arm, however, reached the maximum, and a score at its maximum cannot register such a difference. The failed criterion therefore says more about the instrument than about the students. The ceiling under automatic grading was anticipated, since S4 was fixed in advance and met. That it held in the told-AI arm as well was not. The saturation describes these test suites on these exercises rather than automated testing in general, and tests built to separate students might well do so. For a course that relies on automatic tests, the transferable point is what such a score can carry once it saturates: it can show that code runs, but near the ceiling it ranks students only coarsely. The oral score separates students whom the tests do not. On exercise 2, where 99.4% of the submissions scored 90 or above on the tests, the oral scores of the same students ranged from 15 to 93 (Table 4). This is in line with the observation, made before generative AI, that about a third of introductory students whose programs passed the automated tests struggled to explain their own code (Lehtinen et al., 2021a). Where a model can produce code that passes the tests, a passing score certifies the code rather than the student who submitted it. 

6.3. Running the examination at class scale 

What running the examination required is the practical side of the fea-sibility question. The system examined 247 students in 546 sittings on a single workstation, in two examination languages, and the examiner needed its fallback model on only 3 of 2,192 calls (Section 5.1). Most students (212 of the 247) had a graded examination on exactly two exercises, and without the gradual rollout each would have been examined on all three (Section 4.2). Model spend averaged at most $1.37 per sitting. More important than the amount is how the human work scales. Reviewing the topic pool took two to three hours per exercise, whatever the number of students, and running the deployment took a teaching assistant about 40 hours over the whole semester 42 (Section 5.9). The examining itself, which in an oral examination grows with every student, was done by the system. A human examiner giving the same sittings would have spent about 146 hours in examination alone. Autonomy here has a specific meaning. No member of staff was present in the examination room at any point, and no human reviewed or adjusted a grade before it was recorded. The human check came after the grade instead. Every student could appeal to the teaching assistants, who decided by reading the transcript and the code. Over the 461 cells with a graded sitting, 23 appeals were filed, 13 of them arising from one recurring error, which was corrected for every affected student, including those who had not appealed (Sections 5.1 and 4.5). 

6.4. One sitting or two 

A single sitting is a short basis for a grade of record. A student’s oral scores on two exercises correlate +0.313 (Section 5.6), close to the 0.34 be-tween two oral examinations given by staff in a large course (Ellis et al., 2026). A 16-minute examination by the system was therefore roughly as consistent across sittings as an examination by people. Here the two sittings examined different exercises, so the figure mixes measurement error with real differences in what students understood. The mean of two sittings tracks aca-demic standing more closely than any single sitting, at +0.468 against +0.330 to +0.419, and on the pure computer science track at +0.490 against +0.433 on exercise 3 (Section 5.3), as aggregating measurements would predict. For a course, the practical consequence is that a grade of record is better rested on more than one sitting, and the system makes that affordable: an addi-tional examined exercise costs model spend and one review of its topic pool rather than examiner hours. 

6.5. How students received the examination 

Students began skeptical. Before experiencing either mode, they expected the autograder’s grade to reflect their understanding better than the AI ex-amination’s (Section 5.8). That expectation should be read beside the ceiling described in Section 6.2. Under automatic grading, half or more of every arm scored exactly 100, and with AI assistance permitted, such a grade could be reached with little effort. An examination that asks students to account for their code takes that easy grade away and adds work that automatic grading never asked for: preparing to explain the code, booking a slot and coming to the examination room. Part of the resistance to it may be resistance to 43 that loss and that effort. In the university’s end-of-course teaching evalua-tion, which is separate from this study, several students objected that the system had removed an easy part of a demanding course and added the time needed to prepare and attend, while others described it as the way knowl-edge should be assessed now that AI can write the code. After the exercise 3 examination, for almost all of them their second, students rated the AI ex-amination more positively than they had before it, and support for keeping an AI-based component in grading rose. The first encounter did not show this gain. Students who met the AI examination first, at exercise 1, rated it lower afterwards than they had expected, and those who met it at exercise 2 showed no change. These responses were given shortly after a grade from the system, and the students who answered both forms on exercise 3 had higher oral scores than those who did not (Appendix E). With that caution, they suggest that acceptance came with a second encounter rather than the first. 

6.6. Assessing understanding when AI use is permitted 

Much of the response to generative AI in assessment concerns whether a student used it. ATC asks instead whether the student understands the code they submitted, however it was produced. Students were permitted to use AI assistants, and the grade does not depend on whether they did (Section 3.1). The grade therefore rests on the student’s own account of the code rather than on a judgment about how the code was written, and the design needs no detector of machine-generated code to be fair. A student could prepare by having a model explain their code to them. That preparation is itself study of the code, and the questions are designed so that recalling a prepared explanation is not enough. They are formulated during the examination from specific lines, and they include questions on why the student made a design choice and on what the code would do if an input or a condition changed, which an explanation of what the code does is unlikely to cover (Section 3.3). Authorship is recorded but kept out of the grade. The examiner rates whether the student speaks about the code as its author, and the outcome goes to staff. The two staff reports in Section 3.5 show why the axes are kept apart. Code that looked machine-generated came with an account that scored 92, and a student who could not explain a line of their own script scored 69. Merging the two axes would have penalized the first student for how the code looked, or let a suspicion of misuse decide the second student’s grade. Keeping authorship advisory leaves decisions about misconduct with people, who can weigh evidence the system does not have. Together, these 44 choices bring the oral defense that the integrity literature proposes (Kofinas et al., 2025) to the scale of a full course. 

7. Limitations and threats to validity 

The limitations below bear mainly on the second of the two claims set out at the start of Section 6, that the system’s scores relate to other measures as its design predicts. They are ordered by how directly they bear on it, and for each we state what it affects and what it leaves standing. The clearest limitation is the absence of human-examiner ground truth. No human examiner scored the same students on the same submissions, so we cannot state how closely the oral score tracks the grade a trained examiner would have given after a comparable defense. Where no accepted standard exists, the usual course is to test whether a score relates to other measures as theory predicts (Campbell and Fiske, 1959), and the success criteria were built for that purpose (Section 4.7). Human oral examination is itself a noisy criterion: two oral examinations given by staff in a large course correlated 0.34 within students (Ellis et al., 2026), close to the 0.313 between two sit-tings here (Section 5.6). The grades also met human checks. Throughout the deployment, the course’s two teaching assistants read samples of ques-tions, answers and scores and found them sound, although without a rating scheme or a measure of agreement between them. Every student could ap-peal, and over the 461 cells with a graded sitting, five appeals contested the oral score. All five were upheld, so the oral score was revised in about 1% of cells (Section 5.1). Grading was also stable: re-running the Grader on a fixed transcript reproduced its scores closely, with an intraclass correlation of 0.978 (Section 5.6). Section 8 describes the study that would measure agreement with human examiners. A second limitation concerns the independence of the oral score and the code quality score. Both are model outputs, and the three agents run on the same model and share a prompting style. Separating their inputs limits contamination between transcript and code without making the pipeline in-dependent of itself. A shared model could shape how the two scores relate to each other, but it cannot explain why the oral score relates to grade point average, a measure the system never saw (Section 6.1). One input crosses the separation by design: the Grader receives the Code Reviewer’s style as-sessment for the authorship decision. Whether that input moves the oral score itself was not tested by withholding it. Whatever its influence, it does 45 not drive the central result: holding the assessment constant leaves the oral and code quality scores uncorrelated on all three exercises (Section 5.5). A future implementation could take the authorship decision in a step that does not produce the oral score. Degree grade point average is a coarse external criterion. It aggregates courses that differ in subject, format and difficulty, most of them unrelated to systems programming, and it is not on a common scale across programs. Coarseness of this kind lowers a correlation, so the oral score’s +0.419 is a conservative estimate of its relation to academic standing. Where the scale is common, on the pure computer science track, the coefficient is higher, at +0.433 for a single sitting and +0.490 for the mean of two (Section 5.3). The same criterion limits the three course grades used as benchmarks, which correlate with it at 0.33 to 0.53 (Section 5.7), so the oral score is held to the standard that established measures meet. The analyzed sample also leaves out the weaker end of the cohort: the 21 students who submitted exercise 3 but had not sat it had a lower grade point average (median 78.7 against 83.0). A narrower range of students makes a correlation smaller, so their absence works against the result rather than for it. The deployment is one course at one institution, with one teaching team and one submission format, and the dimensions from which topics were gen-erated and the examiner’s instructions were written for systems program-ming. A single deployment cannot fully separate properties of the design from properties of this cohort. Within it, however, the result repeated: the oral score tracked grade point average on each of three exercises, written in two programming languages, and in two groups of students that shared only two members on exercises 1 and 2 (Section 5.3). The results also belong to one model version, Claude Opus 4.6. A newer model would be a different instrument, but the parts of the design that the results rest on, the separa-tion of inputs and the fixed arithmetic, do not depend on the model, and the criteria fixed in advance can be applied again to a new model at the cost of one deployment. Section 8 notes the further courses in which the system has since been used. The crossover limits what any comparison between the two modes can support. Mode is tied to exercise content within each group (Section 4.2), and the two groups were formed by students’ choice of lecture group rather than by randomization. They differ in size, 84 students against 163, and in track composition, with 63.8% of group L on the pure computer science track against 42.9% of group S (full-cohort denominators). This bears only on the 46 secondary comparisons, of how the modes were received and of automated test scores under each incentive. It does not bear on S1 to S3, which were evaluated on exercise 3, where the whole cohort was assigned the AI exam-ination and the two groups’ oral, code quality and combined grades did not differ detectably (Appendix B). Group is therefore treated as a descriptive stratum, and no group contrast is presented as a causal effect. The examination room was unattended, and the recordings were reviewed by sampling rather than in full. Each student sat at a workstation locked to the examination, two cameras recorded continuously, and every sitting had a chance of being observed (Section 4.5), a more controlled setting than that of the closest deployed system, in which students sat the examination on their own machines wherever they chose (Ipeirotis and Rizakos, 2026). The sampled review found no violation in any sitting it covered. Undetected help during a sitting would also most plausibly have raised the scores of weaker students, which would weaken the relation between the oral score and grade point average rather than produce it. 

8. Future work 

Two kinds of next step follow from this deployment: measuring the instru-ment further, and extending what it can be used for. The first measurement is a comparison with human examiners, which requires a new study rather than further analysis of these data (Section 7). A sample of recorded sittings would be graded independently by human examiners who see the submission and the transcript but not the system’s score or feedback. The sample would be stratified so that the full range of scores the system produced is repre-sented. Agreement would be reported between examiners as well as between examiner and system, since the second figure cannot be interpreted without the first. Acceptance thresholds would be fixed before any grading begins, as the criteria for this deployment were. What counts as acceptable disagree-ment is unsettled for human examiners too, so the design has to state its answer in advance rather than derive one afterwards. A second measurement concerns the examination itself. Grading is al-ready known to be stable on a fixed transcript (Section 5.6), and a student’s two sittings here agreed about as closely as two oral examinations given by staff (Section 6.4). Examining students twice on the same submission, with questions drawn and phrased afresh, would separate measurement error from real differences in understanding and so give the reliability of a single sitting 47 directly. Controlled studies could also measure how far a score moves when the same question is reworded or a fixed set of questions is reordered. A third question is how the examination shapes what students do before it. Students who know they will be asked to explain their code may read it more closely, use AI assistants differently, and come to understand their own programs better. After the exercise 3 examination, students agreed more than they had beforehand that preparing for it deepened their understanding of their code (Appendix E). That is a self-report, and a study of how students prepare would test it, for example by comparing how students work and how they perform on later tasks between cohorts or courses that do and do not examine students on their own code. The transcripts are a further source of evidence. A qualitative reading would describe what the scores are made of, including how a student’s ac-count of their own code develops under questioning. Read across a course, the examiner’s per-answer scores, grouped by the topic and dimension of each question (Section 3.3), could also show an instructor which topics and dimen-sions the class as a whole understood least, and they would do so without further marking. The second kind of next step extends what the system can be used for. The same dialogue could be offered as ungraded rehearsal before the first graded sitting, after which ratings did not rise (Section 6.5), to measure who takes it up and whether the examination proceeds differently without stakes. It could also re-examine a corrected submission: after a failed exercise, the examiner would read the change the student made and question them on what was wrong, what changed and why it now works. Two further courses, outside the scope of this paper, have used the system since the deployment reported here: an introductory programming course, and a linear algebra course in which students scanned their handwritten work and an off-the-shelf tool converted it to text for the examiner. The first required almost no adaptation, and the second some, far less than building the system did. 

9. Conclusion 

Generative AI has made working code weak evidence that a student un-derstands it. This paper shows that a course can respond by asking every student to explain their own code, with no examiner in the room and with a grade of record at the end. To our knowledge, ATC is the first system to bring 48 questioning anchored in the student’s submission together with autonomous examination in a running course (Section 2). The deployment did more than run. Judged against criteria fixed in ad-vance, a 16-minute dialogue produced a score that separated students whom the course’s tests could not, that was unrelated to the quality of the code they submitted yet tracked how they stood across their degree, and that, over two sittings, fell within the range of grades from semester-long courses. The examining itself, the part of an oral examination that grows with every student, was done by the system, and most of the human work that remained grew with the number of exercises rather than the number of students. This changes what a course can ask of work done with AI. Students may use it to write their code, and their grade still rests on what they can explain about that code. The system has since been taken up by two further courses, one of them outside programming, and the comparison with human examiners described in Section 8 is the next step toward using it as widely as the problem it addresses. 

Appendix A. Implementation detail 

This appendix describes how the system was implemented. The deploy-ment ran on Google Cloud Platform: the application on Cloud Run, the managed container service, with examination state in a managed Postgres database and submissions and results in object storage. 

Topic selection and structured output 

The topic selector described in Section 3.3 is deterministic code, seeded separately for each sitting. Its state is kept with the rest of the sitting, as described below, so an examination can be reproduced from its record. Each agent returns its output through the provider’s tool-use interface, which constrains the response to a fixed set of fields, such as a score and feedback for each answer. The system therefore never has to extract a score from free text. 

State, access and operation 

The backend holds no examination state in memory between requests. The entire examination in progress, including the selector’s state, the model message history, the transcript and the current turn, is serialized onto a single database row and reconstructed on each request. Because any instance can 49 handle any request, the service can scale out under load, and an examination continues if the server handling it is replaced partway through. Once the examination ends, the record of the sitting holds the code examined, the full transcript, the examiner’s per-answer scores and authorship ratings, the seed and the temperature, which model answered each call, and the structured outputs of the Code Reviewer and the Grader. This is the audit trail that Section 3.1 requires of a defensible grade. The student’s browser never reaches the backend. The student interface is a web application whose server-side layer is the only component that talks to the backend, which is private and reachable only with a short-lived cre-dential issued by that layer. Nothing running in the browser can therefore call the agents or read stored records directly. The same application image is deployed as student, staff and quality assurance variants that differ only in runtime configuration. Grading runs as a background task after the examination ends and can be re-run for any sitting, which allows recovery from transient failures. In the deployment reported here, each sitting that produced a grade was graded once, and no stored grade was regenerated. A staff console reports grade distributions and flagged cases, shows how often each topic was used, and exports the results table. Once the results pass a completeness check, the system emails each student the grade and the written feedback.

Two are worded identically apart from the name of the mode (T0 and T01), two were adapted to each mode because an autograder returns no feedback (T3 and L1), and two ask about a different aspect of each mode (T1 and T2). Some students submitted the same form on the same exercise more than once: 78 students did so, in 90 instances. The earliest record is used, and the latest is used in a pre-specified robustness check. The four hypotheses that compare the two arms or the two groups (H1, H5, H6 and H10) exclude the five students whose experience on exercise 1 or 2 departed from their group’s arm: the three who sat under the other group’s arm and the two recorded in group L for administrative reasons (Appendix C), and 58 including them changes no verdict. Response was high on the pre-examination AI form (89, 94 and 83 percent of eligible students on exercises 1 to 3) and on the post-examination form at exercises 1 and 2 (81 and 79 percent of those who sat). It was lower on the pre-examination autograder form (60 and 32 percent) and on the post-examination form at exercise 3 (52 percent). Complete pre-post pairs cover 77, 75 and 50 percent of the students who sat, so the exercise-three experience gain rests on about half of that exercise’s cohort. The students who answered both forms also differ from those who did not: on exercise 3 their oral scores were higher (medians 91 and 87, Cliff’s delta +0.167 [+0.012, +0.317]). 

Decision rules. The hypotheses, their measures and their thresholds were written after the deployment and before any response was inspected (Sec-tion 4.7). A hypothesis of a difference is supported when its interval, at the level stated for it, excludes zero and its point estimate runs in the predicted direction. H5, a hypothesis of equivalence, is supported when its interval lies within ±0.15 on Cliff’s delta. Two further conditions apply: at least 30 complete pairs for a contrast within students and 25 respondents per group for a contrast between groups, and an internal consistency of at least 0.70 for any composite. 

Primary hypotheses. The naive expectation gap (H1) asked whether stu-dents, before experiencing either mode, would expect the autograder’s grade to reflect their understanding and mastery better than the AI examination’s. It is tested at exercise 1, the only point at which no student had experi-enced either mode, on the two identically worded items (T0 and T01). The two-item composite gives a Cliff’s delta of +0.305, with a 98.33% interval of [+0.093, +0.490] and p = 0.00046, on 103 respondents to the autograder form and 74 to the AI form. Each item excludes zero on its own: whether the grade reflects understanding, at +0.299 [+0.092, +0.483], and whether it reflects mastery, at +0.273 [+0.066, +0.460]. The adapted accuracy item, which does not enter the decision, gives +0.403 [+0.201, +0.575], but it asks about the accuracy of the AI examiner’s feedback and of the autograder’s grade, so a difference on it may reflect those two objects rather than the two modes. Seven students answered both pre-examination forms at exercise 1 and so appear on both sides of the contrast. Excluding them gives +0.344 [+0.125, +0.531] on 96 and 67 respondents, and a bootstrap that keeps each such student’s two records together gives [+0.089, +0.491] around the same +0.305. 59 The exercise-three experience gain (H3) asked whether students would rate the AI examination more positively after the exercise 3 examination than before it. By then almost every student had experienced both modes and was meeting the AI examination for the second time. Across the eight-item composite (T0 to L3), the matched-pairs rank-biserial correlation is +0.489, with a 98.33% interval of [+0.214, +0.699] and p = 3 .1 × 10 −5, on 107 complete pairs, and all eight item estimates are positive. The retention-support shift (H4) asked whether that examination would increase support for keeping an AI-based component in grading, measured by the preference item P2. The net switch, the share of students who moved to an option that includes the AI examination minus the share who moved away from one, is +0.159, with a 98.33% interval of [+0.034, +0.273] and p = 0.0026, on the 88 of 107 pairs left after setting aside respondents who chose no preference at either end. The pre-specified alternative coding, which counts no preference as not including AI, agrees, at +0.140 [+0.019, +0.252] on 107 pairs. All three primary hypotheses meet the further conditions: each contrast exceeds its minimum sample, and the composites reach an internal consistency of 0.968 for the two-item composite (Spearman–Brown on the polychoric correlation) and 0.960 and 0.955 for the two eight-item composites (ordinal alpha). On the exercise 3 composite, five of the eight items have 98.33% intervals that exclude zero: whether the examiner asks the right questions, whether the grade reflects mastery, whether it reflects understanding, whether the student could present their knowledge fully, and whether preparing for the examina-tion deepened their understanding. The three that do not are whether the feedback helps learning, whether the dialogue deepens understanding, and the accuracy of the feedback. Because the eight items correlate highly with one another (mean inter-item Spearman near 0.69), they do not measure eight distinct attitudes, so the number of items that moved reflects the size of the shift rather than its breadth. Three features qualify these results. H1 compares the respondents to the two forms, who come almost entirely from different lecture groups, and the groups differ in size and in degree-track composition, so the contrast between the two modes is also a contrast between the groups. H3 and H4 were answered shortly after a grade from the system, at a second encounter with the format, and part of the movement may reflect satisfaction with that grade. They also rest on the students who answered both forms, whose oral scores were higher than those of the students who did not. 60 Exploratory hypotheses. Of the seven exploratory hypotheses, one is sup-ported. Students meeting the AI examination after the autograder, at ex-ercise 2, found its questions (T2) more appropriate than they had expected (H2, the question-appropriateness surprise), at +0.355 [+0.126, +0.544] on 122 pairs. One result runs against its prediction. Students meeting the AI examination first, at exercise 1, rated it lower afterwards than they had ex-pected on all eight items, four of them with intervals below zero (H7, the first-encounter gain), at −0.349 [ −0.603, −0.064] on 63 pairs, with 36 stu-dents moving down and 23 up. Satisfaction with a grade would push ratings after the examination up rather than down, so it does not explain this result, but the novelty of the format and the wider spread of exercise 1 scores may. The same eight items were measured in three cells, giving +0.489 at exercise 3, −0.349 for group S at exercise 1 and +0.042 for group L at exercise 2, so the exercise 3 gain does not repeat at either group’s first encounter with the AI examination. Three further exploratory hypotheses are not supported. Before either mode, students showed no detectable difference in how much they expected each to contribute to their learning (L1; H6, the learning-contribution expec-tation gap), at +0.052 [ −0.132, +0.215] on the same 103 and 74 respondents, although this rests on a single item worded differently for each mode. Stu-dents meeting the AI examination after the autograder did not rate it more favorably overall (H8, the broad post-autograder gain), at +0.042 [ −0.179, +0.250] on 122 pairs, although the appropriateness of its questions (H2) is one of the eight items in that composite. Perceived accuracy (T3) did not change detectably at exercise 3 (H9, the accuracy-perception gain), at +0.195 [ −0.077, +0.429] on 107 pairs. The accuracy item is also one of the three items in the H3 composite whose interval includes zero, so H9 adds no independent evidence. The order pair tested whether the order in which the two groups had met the two modes left a mark on their ratings after the exercise 3 examination, across T0 to L3. H5 predicted that the two groups’ ratings would be equiv-alent, within a margin of ±0.15 on Cliff’s delta, and H10 that they would differ. The difference, −0.019 [ −0.264, +0.223] on 35 and 77 respondents, is too wide to support either hypothesis. 

Robustness. Using each student’s latest record instead of the earliest, the pre-specified robustness check, leaves every verdict unchanged. It changes the estimates by at most 0.117, and by about 0.04 at the median. The duplicated 61 records concentrate on the pre-examination AI form and on exercise 2, so the choice of record matters more for some comparisons than for others, but it moves no verdict.
